October 2026

October was mostly one project: moving CleverBound's data out of text files and into its PostgreSQL database. CleverBound is a school boundary planning website I built that assigns neighborhoods to schools based on limits a user sets. The switch went live with every result unchanged and no downtime.

i.

Build

Saturday building time this month went almost entirely to the software engineering phase of my CleverBound roadmap: connecting the app to its database.

Oct 17

Switched the algorithm's data source to PostgreSQL

CleverBound's algorithm used to read school and neighborhood data from text files bundled with the code. I changed it to read from a database I created instead, without changing any results.

Why
With text files, every data update required a code change and a redeploy. The same data already lived in a Supabase database I had built earlier, but integration problems with Supabase's free tier had kept me from connecting the app to it until now. In the meantime, the text files were a duplicate that had to be kept in sync by hand.
How
Wrote a reader module that queries PostgreSQL with psycopg 3 and wraps the rows in a LineSource, a Python str subclass that behaves like the old file path while carrying the data. The existing optimization pipeline ran unchanged, with small edits to four files. The Flask backend connects server-side through the Supabase Session pooler, so row-level security stays closed to the public API, and it returns a 503 if the database is unreachable.

Oct 17

Added per-school-level population data

I added the separate elementary, middle, and high school population figures the algorithm depends on to the database.

Why
The database stored one combined population per neighborhood. After working backward through how the original projections were calculated, I found the combined figure could not reproduce the per-level values.
How
Designed a neighborhood_level_populations table keyed by neighborhood and school level, plus a display_order column to preserve the original ordering. Seeded it with a SQL migration generated from the text files that can safely run more than once and validates its own output.
Result
501 projections (167 neighborhoods across 3 school levels) moved into the database.

Oct 17

Proved the database switch produced identical results

Before touching any live database, I built a test that runs CleverBound's algorithm on the old text files and on the new database, then compares the output.

Why
If a school boundary plan changes because of an internal code change, that is a bug, even if no one can tell why.
How
Restored the production backup into a local PostgreSQL instance, ran the migration there, and wrote equivalence_check.py. It runs 162 planning scenarios through the text-file pipeline, the database pipeline, and a live request to the API, comparing output character by character. As a negative control, I changed one student in the data to confirm the check would fail.
Result
530 of 530 data rows and 162 of 162 scenarios matched, and the one-student change was caught.

Oct 17

Simplified the AI assistant's permissions

I removed most of the custom permission rules I had added in September to Claude Code, the AI coding assistant I use for my projects.

Why
They kept interrupting routine work with approval prompts without adding much protection.
How
Reset the settings to the tool's default auto mode and kept nine deny rules that block it from reading credential files (SSH keys, AWS keys, and its own login token) and from editing Git hooks.
  • Claude Code
Oct 24

Released the database switch to production with no downtime

I rolled out the move from text files to the database in stages: the test database first, then the live database, then the new backend code, checking the results at each step.

How
Each database had its own migration script (the update that adds the new tables and columns) that refuses to run unless the connection string matches that Supabase project's ID. Each migration ran as one transaction that rolls back if any neighborhood is missing data. I ran the production commands myself rather than through the AI assistant. I set the database connection string, DATABASE_URL, on Render, where the backend is hosted, before merging so the deploy had its connection ready, then merged the pull request.
Result
The 162-scenario check passed against both the test and production databases, and the site stayed up the entire time.

  • Supabase

Oct 24

Made district settings data-driven

Adding a school district or changing its settings is now a database update instead of a code change.

Why
The district list, input limits, and default values were hard-coded in three frontend files and in the backend, and they had to be kept in sync by hand.
How
Added a backend function that reads the districts and leveled_districts tables, only offers school levels with complete data, and caches the result for five minutes. It powers request validation and a new public GET /districts endpoint. In the React frontend, I deleted the three hard-coded files and loaded the options from that endpoint, with a loading state and a retry link.
